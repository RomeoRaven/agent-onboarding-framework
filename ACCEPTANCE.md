# Manual onboarding acceptance

Keep a compact outcome record with the destination's owner. Do not put local facts, refusals, task transcripts, or private source inventories in the generic repository. If a check fails, correct its owning source and repeat the affected checks before consequential work.

Evidence levels are distinct: a static package preflight is a check of literal file references; destination acceptance is proof of one bound agent's behavior; independent portability is proof that a different human or harness can follow the generic method. None implies the next. The optional `scripts/check-onboarding.py` reports only static findings. Keep the manual checks below even when it passes.

1. Bootstrap and injection: in a fresh session observe the actual native loader/config or trace, record the installed contract path and injected files/identifiers (including overrides), then separately follow each explicit link from contract to manifest directly or through `START_HERE.md`. A human without this conversation must be able to repeat the route. If native injection is not observable, mark that claim unverified; a successful manual read is not proof of injection.
2. Loaded/read set: record each required framework, personal, system, and source owner (plus conditional persona/memory/project sources), its exact location, verified revision or stable version, owner, and whether it was injected or fetched later. Confirm no required source is missing, duplicated, or unverified and no copied template comments/placeholders remain. Do not call onboarding accepted with an unverified required loader claim.
3. Reconciliation: when a destination had existing agent instructions or owner files, record keep/link/scoped-edit/new/omit dispositions, the approved focused diff (if edited), and the rollback route. In a fresh session prove at least one relevant pre-existing local instruction still works alongside the new manifest route. If the existing file or owner could not be inspected, or a material conflict remains, do not replace it or accept onboarding.
4. Authority: the agent explains personal, destination, and project owners; how to resolve a conflict; and why Markdown order cannot grant permission.
5. Source and method lookup: successfully open one canonical source declared in `SOURCES.md` or the manifest-declared existing source map using its authorized access route. For the bounded task, select one relevant workflow, skill, or runbook from the destination's declared discovery route (or explicitly record that no specialized method applies). Record its owner, status/compatibility, whether a skill is installed or source-only, and the actual native loading or manual-read path; exercise an applicable stop condition. A file's presence or catalog row is not proof that a runtime loaded it.
6. Boundary: present one deliberately out-of-authority request without carrying it out. Record the refusal and the correct owner/approval route; do not test with a harmful live action.
7. Capability and recovery: complete one small, realistic, authorized task, with readback in its owner surface. If a dated handoff exists, confirm its suggestion does not choose the next task and check material old claims against the live owner.
8. Disclosure: review both prospective package contents and any staged changes before the first commit. The generic history must have no personal/local material; the private profile must have no secrets, exact host routes, volatile state, sessions, or raw memory. If material was distributed, assess exposure; a history rewrite cannot recall copies.
9. Independent portability (separate claim): a meaningfully different agent/harness or human-led path follows these instructions without modifying generic files. For generic usability, create a fictional/private profile from the guide rather than use an unapproved real candidate. Record which test used synthetic versus approved real profile, and what required adaptation, at the destination. This is required before claiming cross-harness portability, not before a single destination can be accepted on its own evidence.
10. Permission reality: confirm the destination's actual filesystem, credential, publishing, and service controls independently of document claims.

Accept one destination only when checks 1–8 and 10 pass for that destination, or explicitly keep it unaccepted with the failing check, owner, and next safe route recorded locally. Claim independent portability only after check 9 also passes. This is manual evidence, not an automated compliance certificate.
