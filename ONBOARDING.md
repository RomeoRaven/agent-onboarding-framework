# Onboarding method

## Inputs and owners

The generic framework owns only the method, complete neutral templates, and validation questions. Its root `AGENTS.md` governs editing this repository; `templates/AGENTS.template.md` is inert here and becomes the destination contract only after authorized local adaptation. Personal preferences and approval boundaries belong to their existing operator owner or an explicitly reviewed private representation. Destination-owned files describe the local runtime, source routes, actual limits, and any durable role. Project truth stays with its project.

Start from the destination's actual native loader/config, verify the installed contract path, then follow the exact link to the local manifest directly or via an optional `START_HERE.md`. Record the precise revision or stable, owner-verifiable version of required sources. The manifest declares intended onboarding sources, but native loaders may also inject other context: inspect applicable overrides and do not claim that unlisted files cannot load. Distinguish native injection from later document reads; if injection evidence is unavailable, mark it unverified. Do not float to the latest package without review. Keep completed personal and local files outside the generic repository.

## Authority is not file order

The runtime's governing instructions and real permissions take precedence over Markdown load order. Personal rules govern preferences/approvals within their authority; the destination governs its runtime and local constraints; projects govern their project facts. A scoped file may add specificity or a stricter applicable constraint, not grant unavailable access or silently replace another owner's rule. Resolve apparent contradictions by owner and scope; stop consequential work if a material conflict remains.

## Reconcile with what already exists

The templates are candidate content, never replacements by default. Before installing or refreshing, inspect the destination's native loader/config and every applicable existing agent instruction, override, persona, memory, system/source map, and project rule. Find the owner and scope of each, and preserve their current content and a rollback route under the destination's normal versioning policy. See `guides/CREATE-DESTINATION-FILES.md` for the human walkthrough.

Compare the template's jobs against those existing owners. Keep an existing `AGENTS.md` or native contract intact when it already supplies project/local instructions: add only a missing link to the local manifest and any nonduplicated working-contract behavior that the owner approves. If it already does the job, leave it unchanged and declare its exact route in the manifest. Do not install a second competing instruction file or copy the generic framework's root `AGENTS.md`. Use the same keep/link/merge/omit decision for other local files; persona and memory remain conditional. Never let a portable profile replace a reachable authoritative personal source.

For each proposed change, show the destination owner a focused before/after diff and disposition: retained local rule, linked owner, scoped addition, or omitted duplicate. Resolve material conflicts by scope and owner before mutation; do not pick the last-loaded text. If an existing file cannot be read or its owner/loader is unknown, stop consequential integration rather than overwrite or infer. Apply only authorized edits in the destination's owner surface, retain a rollback route, then test in a fresh session that original local behavior still works and the new manifest path, source lookup, refusal, and bounded task work. Record the resulting version and disposition locally; generic files never receive completed destination copies.

## Run and refresh

Use `guides/CREATE-OPERATOR-PROFILE.md` only if no suitable personal owner source exists. Use `guides/CREATE-DESTINATION-FILES.md` to bind the near-ready local contract, manifest, system facts, and source routes. A persona and Tier 1 memory pointer are optional only with verified native loading and a real role/routing need. The portable `workflows/memory-routing.md` classifies compact pointers, on-demand methods, and dated evidence; `workflows/session-continuity.md` governs selective recovery and handoffs. Task context stays with its project/task owner, not a copied general profile.

When an owner source changes, repeat only the affected reconciliation against its private representation and destination manifest, explicitly update the recorded revisions, and rerun affected acceptance checks. A required file that is inaccessible, unverified, duplicated, or materially contradictory blocks consequential work. No agent may fabricate missing identity, authority, route, or role information.

No install script, provider, model, or loader is required. Any runtime-specific context adapter and enforcement belong at the destination.
