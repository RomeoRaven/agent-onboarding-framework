# Continuous improvement — portable method

Use during ordinary work when avoidable friction, weak proof, unclear ownership, repeated effort, a near-miss, or a better future path becomes visible. Use as an explicit improvement task when the operator requests it. This method must not turn every task into an audit, background job, telemetry system, or unauthorized change.

## Notice and classify

At natural boundaries—before an avoidable repeat, after surprising output, and before closeout—ask whether future work could become easier, safer, clearer, or more reliable. Name the concrete current friction and the better future behavior, not just a preference for more documentation. Check whether an existing owner, skill, workflow, runbook, helper, or source map already solves it.

Route the opportunity to the narrowest owner:

- Ordinary procedure or discoverability friction: improve the existing procedure or pointer where future agents will encounter it.
- Repeated agent-behavior or trust-impacting failure: identify the future-loaded control and its real owner; use that destination's reliability/control process rather than inventing global enforcement here.
- Domain/product problem: keep it with the domain or task owner. A future improvement that would derail the requested outcome belongs in that owner's tracker, not in memory or an unrelated new workflow.

## Choose and act

1. Compare leaving the current owner unchanged, fixing it now, and recording a follow-up. Choose the right-sized intervention with the highest expected future benefit and least new maintenance.
2. Stay inside the current request and approval boundary. Fix a low-risk, in-scope owner-path defect when authorized; otherwise give a concise proposal naming the cause, recommended change, owner, approval needed, and proof that would show it worked. No instruction here grants permission to change shared controls, public material, services, credentials, or another destination.
3. Before creating a new process artifact, apply `workflows/workflow-and-skill-maintenance.md`: check overlap, choose one owner, and prefer a focused edit or link when sufficient. Avoid duplicate checklists and always-loaded rules.
4. Verify the future path, not just the edited text. Can the relevant agent discover or load the corrected owner at the point of use? Did the change preserve the original task and existing constraints? If not proven, describe the limitation and route the next test to its owner.
5. Return to the requested task. Record only a material landed/routed improvement or a useful no-change decision; do not manufacture improvement receipts for every interaction.

## Stop conditions and result

Stop this branch when the opportunity is one-off, the existing owner suffices, the expected benefit is below its maintenance cost, or the next action requires approval or would materially change task scope. An explicit sustained improvement request can have a larger agreed depth and stop condition; it still cannot bypass destination authority. Success is a validated change in a future work path, a well-owned follow-up where change is gated, or an honest no-op—not a list of issues found.
