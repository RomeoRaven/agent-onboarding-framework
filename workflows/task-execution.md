# Task execution — portable method

Use for a substantive request after the destination's native instructions, operator authority, and source map are reachable. This is the ordinary work loop, not a substitute for a domain workflow or the runtime's permission system. For a simple question, answer from the needed sources without creating a task, plan, or receipt merely to satisfy this method.

## 1. Frame the work

- Let the current operator request choose the outcome. Separate a question, evaluation, recommendation, and explicitly authorized change; a desired result or prior handoff does not by itself approve a later implementation stage.
- State a working success test: the usable result, relevant scope and exclusions, required evidence, and stop/approval boundary. Make low-risk interpretation choices yourself; ask only when an ambiguity changes authority, safety, outcome, or owner.
- Find the live owner of open work and project truth through the destination's source map. Old handoffs and summaries are leads, not current state. A tiny one-off request need not create a tracked item; real deferred obligations belong with their task owner, not in memory or this framework.

## 2. Find the method and authority

- Check the destination's declared workflow, skill, runbook, and checker routes. Open the matching owner on demand; verify its status, scope, compatibility, and actual loader. An index entry or installed skill name is discovery, not proof that its procedure was loaded or its tools are available. Use `guides/USING-WORKFLOWS-AND-SKILLS.md` for the selection questions.
- Name applicable operator, destination, role, and project owners. Instructions loaded later are not automatically more authoritative. Missing access, a material contradiction, or an unverified required owner blocks consequential work; do bounded read-only diagnosis and report the resolution owner.
- Choose a proportional path: direct answer, bounded evaluation, authorized execution, or a decision packet when the operator genuinely must choose. Do not transform evaluation or a question into permission to mutate. Obtain the destination's required approval before writes outside the authorized scope.

## 3. Execute and prove

1. Inspect the exact target and its present state before changing it. Use the existing owner procedure and the narrowest reversible action that can achieve the accepted outcome; do not silently take adjacent work because it is attractive.
2. Decide proof before claiming completion. Scale it to the risk: inspection for low-risk text; a smoke or realistic scenario for behavior; a boundary test where failure is costly. Use a destination-owned checker when one exists. If a finding is unrelated to the accepted result, report or track it rather than expanding the task.
3. After a write to an external system, read back the exact target and confirm the intended effect. For code or local artifacts, exercise the behavior or run the relevant tests; a saved file or successful command is not itself the user-facing result. If proof is unavailable, say what remains unverified.
4. Capture any true deferred work at its single active task owner with an action, owner, and blocker/proof link. Do not close a parent item while required follow-up exists only in prose; do not create a parallel task system.

## 4. Close at the right depth

Report what the operator can now use or decide, material limits, proof location, approval boundary, and next action. For restart context, use `workflows/session-continuity.md`; for persistent knowledge, use `workflows/memory-routing.md`. A dated handoff is conditional, not the default for every task. Notice improvement opportunities without replacing the current outcome; use `workflows/continuous-improvement.md` only for a right-sized, in-scope improvement or owner-routed follow-up.

## Stop and validation

Stop before consequential action if the current request does not authorize it, the target or owner cannot be identified, a governing source is missing or contradictory, the destination lacks the tool or permission, or the proposed action would change the accepted outcome. Success means the claimed result is observable at its owner, the required boundary was respected, and a future reader can find any unresolved commitment at its task owner. Do not label research, a plan, a test count, or a confident summary as implementation.
